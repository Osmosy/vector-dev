# Стандарты команды в spec-kit

[spec-kit](https://github.com/github/spec-kit) — открытый набор процессов для агентской
разработки: конституция → спецификация → план → задачи → реализация → сходимость. Полезен
структурой, но его шаблоны описывают чужой способ принимать работу: там «приёмка» — это
пользовательские сценарии и чек-лист, а не код выхода чекера.

Этот каталог содержит наш пресет: правила «Вектор разработки» в формате spec-kit плюс чекер,
который переводит вентили Г3 в машинную проверку.

## Что внутри

| Файл | Что делает |
|---|---|
| `preset/preset.yml` | пресет `vector-dev`: подменяет 5 шаблонов spec-kit |
| `preset/templates/constitution-template.md` | конституция: П-01…П-13, этапы Г1–Г5, KPI, коды выхода |
| `preset/templates/spec-template.md` | спека: REQ-коды, источники с sha256, фальсифицируемые проверки |
| `preset/templates/plan-template.md` | план: карта требований, контракты, вентили этапов |
| `preset/templates/tasks-template.md` | задачи: обязательная ссылка на REQ и команда проверки |
| `preset/templates/checklist-template.md` | чек-лист приёмки с кодами 0/1/2/3 и журналом |
| `check_spec.py` | чекер спеки: 8 вопросов, коды 0/1/2/3 |
| `selfcheck.py` | 7 сценариев самопроверки чекера |

## Установка

```bash
uv tool install specify-cli            # или: uv pip install specify-cli
specify init my-project --integration claude
cd my-project
specify preset add --dev ~/projects/vector-dev/spec-kit/preset
specify preset resolve spec-template   # проверка: сверху должен быть vector-dev
```

Дальше — как обычно в spec-kit: `/speckit-constitution`, `/speckit-specify`, `/speckit-plan`,
`/speckit-tasks`, `/speckit-implement`, `/speckit-converge`. Отличие в том, что шаблоны этих
команд — наши, а не апстримовые.

## Чекер

```bash
python3 spec-kit/check_spec.py --root . --json
python3 spec-kit/check_spec.py --root . --feature 001-demo
```

Что проверяет (все находки блокирующие):

| Q | Вопрос | Что ловит |
|---|---|---|
| Q1 | коды REQ уникальны и вида `REQ-0001` | копипаста блока требования |
| Q2 | у требования есть источник и приоритет | требование «из воздуха» |
| Q3 | у требования есть проверка, которую можно провалить | «работает хорошо», «стабильно», «удобно» |
| Q4 | требование есть в plan.md | спека шире плана |
| Q5 | требование есть хотя бы в одной задаче | требование, которое никто не делает |
| Q6 | нет задач на несуществующее требование | план разошёлся с реестром |
| Q7 | не остались плейсхолдеры шаблона | `[FEATURE NAME]`, `<команда>`, `TODO` |
| Q8 | у каждого источника sha256 и дата | «дока про эту версию» без версии |

Коды выхода: 0 — принято; 1 — блокирующие находки; 2 — плохой вход (нет `specs/`, `spec.md`,
`plan.md`, `tasks.md`); 3 — отказ запускать (найден `acceptance/checker.sha256` и он не совпал
с чекером — проверку подменили).

Чекер ничего не меняет: он только отчитывается. Код 3 отделён от 1 намеренно: «проверка
сломана» и «работа плохая» — разные решения.

## Самопроверка

```bash
python3 spec-kit/selfcheck.py
```

Семь сценариев на временных копиях: чистая спека → 0; требование без проверки → 1; требование
выпало из задач → 1; задача на несуществующее требование → 1; незаполненный плейсхолдер → 1;
нет спек → 2; подменённый чекер → 3.

## Чем это отличается от апстрима

| Апстрим spec-kit | Наш пресет |
|---|---|
| приёмка = сценарии в спеке и чек-лист | приёмка = код выхода чекера, чек-лист только фиксирует |
| спека первична | реестр требований первичен, спека — кэш с рёбрами `supersedes` |
| тесты опциональны («only if explicitly requested») | замороженный набор тестов и чекеры — обязательны, менять их в акте с кодом запрещено |
| «качество» как принцип | KPI как требование на 100 % с областью и базой |
| три исхода | четыре кода выхода: 0 / 1 / 2 / 3 |

## Ограничения

- Пресет подменяет шаблоны, но не команды. Команды spec-kit ожидают свои разделы
  (`User Scenarios`, `Requirements`) — наши шаблоны сохраняют эту логику, но пишут по-русски,
  поэтому формулировки в командах могут требовать правки при обновлении апстрима.
- Проверено на `specify 1.2.5` (апстрим в разработке: `1.2.6.dev0`).
- Чекер читает markdown регэкспами: нетипичная разметка (таблица вместо списка полей) даст
  находку, даже если по смыслу всё заполнено. Это осознанный компромисс — предсказуемость
  важнее всеядности.
